# 03 · AI: onboarding and the workspace assistant

Code: `packages/ai`. Models are set in one place (`packages/ai/src/models.ts`).

---

## 1. Principle: the model proposes, code decides

No model output is trusted as-is. Every AI answer is schema-constrained JSON, then checked by deterministic code that cannot be talked out of its rules:

- **Onboarding**: the model writes a small *Blueprint Plan*; code assembles the real blueprint (ids, defaults, grants, references) and the validator checks it. Errors go back to the model as precise, located messages; after three rounds the salvager removes whatever still fails, so the result is **always** a valid blueprint.
- **Assistant**: the model calls tools; reads go through the person's permissions, writes are proposals that run through the command pipeline (validation, rules, approvals) only after the person confirms.

## 2. Models

| Job | Model | Notes |
|---|---|---|
| Interview, file reading, design, repair, assistant | `gemini-3.8-flash` | Tested with schema-locked output |
| Routing, column typing, short labels | `gemini-3.5-flash-lite` | Cheap; answers are always checked |
| Design and repair (upgrade) | `gemini-3.1-pro-preview` | Needs billing on the AI Studio project |
| Search, fuzzy matching | `gemini-embedding-2` at 768 dimensions | Matches the Firestore vector index |

No OCR model: Gemini reads scans, photos and PDFs directly; spreadsheets are parsed by code.

## 3. Onboarding

```
interview (Flash, chat)      → Business profile  (facts, each from the person or a file)
files (Flash, multimodal)    → more facts in the same profile
design (Flash/Pro)           → Blueprint Plan    (enum-locked to the catalogue)
assemble (code)              → Blueprint         (ids, defaults, references, grants)
validate (code)              → issues with paths
repair (Flash/Pro, ≤3 rounds)→ corrected plan
salvage (code)               → drop what still fails, report it
review (person)              → create workspace
```

The plan refers to everything by key, never by id. Module, submodule, extension, preset, record, field-type and permission values are enums generated from the catalogue, so the model cannot invent them.

## 4. Workspace assistant — "a model per business" without training

Each question is answered by the same Gemini model given:

1. **Knowledge**: a system prompt generated from the workspace's live blueprint (business, modules, record types and fields, statuses, rules, roles).
2. **Data tools**, generated from the compiled blueprint and limited to what the person's role can see:
   - `search_records(record, where?, order_by?, limit?)` — `where` is a Shapewise expression, type-checked against that record type
   - `get_record(record, id)`
   - `summarise(record, measure, field?, where?, group_by?)` — count, sum, average, min, max
   - `propose_change(...)` — create, update, run an action or convert; shown to the person, executed through the pipeline only when they confirm
3. **Conversation history** of this chat only.

Nothing is fine-tuned or stored in a model; knowledge is always current, permission-scoped and confined to one workspace.

## 5. Testing

- Assembler, salvager, tool execution and prompt builders are deterministic and unit-tested without network.
- `pnpm --filter @shapewise/ai eval` runs live evaluations: business descriptions → blueprint (first-pass valid, valid after repair, salvaged, expected features present) and assistant questions against seeded data.
