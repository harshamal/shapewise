1Product and scope

Shapewise is a business system for small and medium manufacturers. The owner describes the factory and uploads what they already use: spreadsheets, photographed job cards, QC sheets and invoices. Shapewise becomes a working system for that factory, covering sales, purchasing, inventory, production and accounting, with their data already inside it.

What it does

CapabilityWhat the owner experiences
Build from description and filesAn interview of up to 8 questions plus file uploads produces a full system in about a minute.
Run the factorySales orders, purchase orders, goods receipts, production jobs by stage, QC, stock, invoices, payments, and the books.
Change by asking"Add a dyeing stage", "POs over 500k need my approval". The change is previewed, applied without losing data, and can be undone.
Insights and recommendationsWhat to produce this week, what to reorder, where scrap and defects come from (by machine, shift, operator).
Delegate to AI agentsEvery factory gets its own MCP server. Agents operate within roles, and risky actions wait for approval.

2Design principles

PrincipleWhat it means in the build
1. Never generate what must never be wrongMoney, stock, numbering, permissions, approvals and audit live in fixed, tested engines. AI can never change how they count.
2. Configuration, not codeAI produces a validated blueprint (JSON). One runtime executes every blueprint. No generated code anywhere.
3. One writerEvery write from the web app, the assistant or an MCP agent goes through one command pipeline. One set of rules for everyone.
4. Every change is previewed and reversibleBlueprint changes become versioned diffs with a data-impact preview and an undo point.
5. Humans and agents follow the same rulesAn agent can never do what its role can't, and risky actions always need approval.
6. Start from realityLearn from the owner's own files, not only from what they remember to say.
7. Google-nativeFirebase and Google Cloud for every service; Gemini and Gemma for every AI task.
8. Designed, not generated, UIOne fixed design system for every blueprint: neutral palette, one accent, two font weights, dense tables, no gradients or decoration.

4The layered blueprint

The blueprint is the single description of a factory's shape. It is the only thing AI is allowed to write. Each factory's live blueprint is built from three layers.

1 · Base blueprint
Written and tested by us. Sales, purchasing, inventory, production, accounting, approvals, standard roles, default screens and dashboards.
2 · Industry pack
Plastics, garments, food, furniture… Stages, specs, QC checklists, units, metrics. Picked by AI or generated for a new industry.
3 · Customisations
This factory's own changes, from onboarding and every later request. Stored as a list of overlay operations, not a copy.

4.1 Merge and versioning

  • Everything in the blueprint has a stable ID (fld_7k2, ent_job, stg_dye). Keys and labels can change; IDs never do.
  • Packs and customisations are overlay operations: add, update, remove, disable, move, each targeting an ID.
  • live = merge(base@v, pack@v, overlays), then validated and compiled. Every applied change creates an immutable version with author, reason and undo pointer.
  • When we improve the base or a pack, factories get the improvement on their next merge. If an overlay touches something the base removed, the change is flagged for review rather than applied silently.

4.2 What can change, and what can't

Dynamic add, edit, remove or turn offFixed enforced by engines
Fields on any record, including computed fieldsHow a posted document affects the ledger and stock
Modules (add "Machine maintenance", turn off "Quotations")Double entry, gap-free numbering, tax maths
Submodules and steps (skip GRNs, add a dyeing stage)Posted records are reversed, never edited
Workflows: states, transitions, required fields per stepAccounting can be simplified in the UI, not turned off
Approval flows, conditions, approvers, order of stepsSafety floors on approvals can be tightened, never loosened
Roles, permissions, row-level scopesPermission checks can't be skipped by any caller
Rules: discounts, validations, alerts, auto-calculationsAudit log is append only
Screens, dashboards, reports, document templates, number formatsUnits, quantities and money stored as exact integers

4.4 Validator rules

  • IDs and keys unique; references point to existing entities; only catalogue field types and expression functions.
  • Entities touching money or stock must bind to an engine and can't redefine its posting behaviour.
  • Workflows reachable and terminating; transitions name existing states; required fields exist.
  • Approval and permission rules can't drop below engine safety floors.
  • Expressions are parsed and type-checked by our own safe language; no arbitrary code.
  • Every error carries a JSON path and a fix hint, which the repair loop feeds back to Gemini.

5Command pipeline

The single writer for everything. This is what keeps the system consistent no matter how many surfaces or agents are added.

Web UI ──────┐
Assistant ───┼──▶ execute(command, actor)
MCP agent ───┘
   1  resolve tenant + actor (uid or token) + channel (web | assistant | mcp)
   2  load compiled blueprint (cached by tenant + version)
   3  validate input against compiled schema
   4  authorise: role permission + row scope
   5  approval policy: matches? → write approval request, return pending_approval
   6  idempotency key check
   7  Firestore transaction:
        read affected docs, check versions
        engine logic (stock, production, ledger, numbering)
        update computed dependents + rollups
        write audit entry + outbox event
   8  commit → return result (or retry on contention)
Command kindExamples
record.create / updateCreate customer, update a job's mould number
record.transitionMove a job from moulding to trimming (checks required fields and QC)
engine actionpost_invoice, receive_goods, issue_materials, receive_output, record_payment, adjust_stock
approval.decideApprove or reject; on approve, the original command is re-validated and executed
blueprint.applyApply an approved change; creates a version and possibly a backfill job

6.2 Staying fast with dynamic fields

  • Stable field IDs: renames are metadata-only, with no data rewrite.
  • Typed index slots: filterable or sortable fields are assigned to idx.s1–s8, n1–n6, d1–d6, r1–r4. One fixed set of composite indexes serves every tenant and blueprint, so we never hit Firestore's index limit.
  • Computed fields materialised on write, using the compiler's dependency graph. No read-time fan-out.
  • Dashboards read rollup documents, never scan records. Count and sum aggregation queries cover ad-hoc questions.
  • Search: prefix tokens for instant lookup; Firestore vector search with Gemini embeddings for fuzzy matching.

6.3 Isolation and correctness

GuaranteeHow
Tenants never see each otherPath isolation under tenants/{tid}; Security Rules on custom claims; clients read only, never write; server builds every path through one tenant helper
Debits equal creditsLedger engine is the only writer; refuses unbalanced entries; lines embedded so an entry is atomic

Gap-free numberingCounter incremented in the same transaction that issues the document

7Approval engine

Approval flows are blueprint data, so any action can have one, defined by the owner in plain words and applied through the change studio.

8.3 Guardrails (enforced in code)

  • AI writes only blueprint overlays and tool calls. Never SQL, code or accounting logic.
  • Every AI output is schema-validated before use.
  • File contents, record values and tool results are wrapped as data; agent instructions forbid following text inside them.
  • Risky actions park for approval regardless of who asks.
  • Every AI decision that changes the system is logged with its inputs and the human approval.

Security

  • Each token belongs to one tenant and one role; only tools the role can use are listed.
  • Risky tools return pending_approval with an ID; the owner sees it in the approval queue.
  • Rate limits per token; every call audited with the client name; tokens revocable in settings.
  • A read-only demo token for judges.
